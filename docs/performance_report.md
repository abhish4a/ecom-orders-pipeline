## What differs between the two jobs

| Technique | Baseline | Optimized |
|---|---|---|
| Dimension joins (RI check + enrichment) | sort-merge join: the 1M-row fact is shuffled and sorted for **each** of the 2 joins | `broadcast()` hint: customers/products are copied to every task and the fact is not shuffled |
| `spark.sql.shuffle.partitions` | 200 (default), AQE off | 8, AQE on (coalesces small partitions) |
| Column pruning | raw string columns + `raw_record` JSON carried through dedup | only the 14 typed columns needed downstream are selected **before** the dedup shuffle |
| Dedup | `groupBy(max(struct))` + join back + `dropDuplicates`: 3 wide steps | one `row_number()` window: 1 shuffle |
| Write | no repartition: every shuffle partition writes a file per `order_date` | `repartition(order_date)`: one file per partition directory |

## Why the optimized job is faster

1. **Broadcast joins remove the biggest shuffles.** The dimensions are tiny (thousands of rows), but a sort-merge join has to hash-partition and sort the *fact* table on the join key. Broadcasting the dimensions turns both joins into map-side hash lookups.
2. **Fewer bytes per shuffle.** Pruning to typed columns before the dedup means the `raw_record` JSON and raw strings (the widest columns) are never written to shuffle files. That shows up directly in the shuffle write/read rows above.
3. **Fewer wide transformations.** The window-based dedup needs one exchange instead of three.
4. **Right-sized partitions.** On a 4-core laptop, 200 shuffle partitions mean hundreds of tiny tasks per stage (scheduling overhead) and, at write time, hundreds of small Parquet files. Sized partitions plus AQE coalescing and `repartition(order_date)` give one file per day partition, which is also faster for downstream readers.

Stage counts are similar because both variants share the cache, count and write steps, and AQE adds its own stages. The difference is in the work *inside* the stages: tasks and shuffled bytes. The publish step (merge-by-key, staging, swap) is the same code in both variants and is not part of the comparison.

Caveats: local mode on a single machine. Shuffle data never crosses a network here, so on a real cluster the gap from avoiding shuffles is usually *larger*. Timings vary a few seconds between runs (see min/max), which is why medians over several runs are reported.
